#### Verdict

The research correctly preserves counterevidence: repaired upstream defects are not presented as current vulnerabilities; source manifests are not called released artifacts; provider-oriented contracts are described as design tradeoffs rather than broken SDKs. The accepted four contexts, PostgreSQL S2, native custody owner and public implementer obligations remain intact.

#### R1-E01 — medium: make the alternatives comparable for one concrete decision

**Locations:** modularity §§6–7; frameworks §5.

The topology rows mix dimensions that can coexist: a capability-family package can have subpath exports, separate optional adapters and independently versioned feature packages when those are genuinely independent families. Likewise independent SemVer, a qualified release train, lockstep numbers within a family and an N/N−1 support window are not mutually exclusive architectural properties. A reader cannot choose A/B/C without knowing which concrete family, install closure, consumer and support promise changes.

The G3 SDK shortlist also varies both ecosystem and execution profile. An in-process cooperative TypeScript harness and a native-owned external Python/.NET harness do not have the same failure boundary or deployment cost. These are reasonable candidate scenarios but not an evidenced market-wide top three or comparable security promises. Native packaging/signing/operational costs are excluded explicitly, which is honest; that exclusion must remain visible beside the scores.

**Small correction:** label these as scenario bundles/decision rules, or specify a single hypothetical next family with the same caller contract, real consumers and required effects before comparing package configurations. Give each row the same supported behavior, list any different guarantee explicitly, and keep the ecosystem decision conditional on a real consumer. Explain why Vercel HarnessAgent/OpenHands/PydanticAI are outside this particular G3 shortlist instead of implying they lost a universal ranking. No owner question is needed until that consumer exists.

**Counterexample:** one capability family uses two exported subpaths and an optional transport package, independently versioned, released in a qualified all-owner train with an N/N−1 client window. It simultaneously fits several current rows. Treating those rows as exclusive choices would manufacture a disagreement and double-count support cost.

**Scoring implication:** keep complexity as burden, reliability as achievable correctness within the named scope and confidence as confidence in fit. Do not interpret 8 vs 7 as a measured framework difference. LOC confidence 3–4/10 is appropriate until the family inventory exists; the package/release/portable-kit LOC tables overlap and must not be added.

#### R1-E02 — medium: workflow retry configuration is insufficient to qualify crash replay

**Location:** durability §7, especially C (Restate) and the shared retry/unknown wording.

The pinned Restate source explicitly states that `ctx.run` can re-execute the most recent action after a crash between external success and journaling. Disabling or bounding retry-on-error does not establish that this crash replay will never invoke the closure again. The current sentence that runtime calls with unknown outcomes must not receive uncontrolled retries names the intention but does not establish a compatible boundary.

**Small correction:** B/C remain unqualified optional consumer integrations until a concrete public runtime method is demonstrated repeat-safe with the same trusted `(tenant, project, commandId)` and input fingerprint across engine replay. A duplicate receipt/observation must never confer dispatch ownership; a different payload with the same key must reject; key retention must cover every supported workflow replay/restore horizon. A new key on each worker/process attempt is forbidden. Where the chosen public method lacks that contract, the integration must refuse/defer that path, not add a second effect journal or quietly relax ordinary rules.

The baseline S2 brief already distinguishes safe observation from authority: lines 254–258 define scoped command uniqueness and readback as identity/observation only; lines 333–340 permit specific bounded reads for settlement, never dispatch. The phrase “no automatic readback” in the research should be scoped to the forbidden recovery path and must not accidentally forbid these existing owner-authorized settlement observations. Conversely, permission to read does not authorize a workflow wrapper to launch, retry a claim or reconcile private owner state.

**Required kill case:** runtime accepts and starts the operation; wrapper/process dies before the workflow engine journals the returned result; recovery invokes the same integration again; physical dispatch count remains one and the recovered caller receives only the permitted observation/uncertainty. Repeat with a different payload, lost runtime receipt, expired dedup horizon and restore from before the effect. If retained idempotency is unavailable, activation of this integration profile is refused.

**Scoring implication:** proposed reliability 8 can be a target conditional on that contract; Restate fit confidence should remain low/moderate until the actual API and replay test exist. The issue is our future wrapper, not an undisclosed Restate bug. Temporal has related identity/retry concerns, although disabling Activity retries changes its operational behavior differently; do not state both engines have identical retry controls.

#### R1-E03 — medium: bound the observer parity test to equal deterministic inputs

**Location:** durability §3.3 and its proposed off/on-observer experiment.

The LangGraph regression is correctly established: tools observation changed task return behavior, and paused control flow was rendered as failure. It supports semantic parity, not equality of arbitrary real-time executions. Observation may legitimately add latency, exert declared backpressure or consume a finite resource budget; under a deadline or admission limit, two live runs may have different outcomes without a logic defect.

**Small correction:** use a deterministic fixture with fixed clock/IDs/provider replies, identical accepted inputs and sufficient declared budget. Compare canonical domain decisions, returned task value and authorized dispatch/effect counts. Test overhead, bounded queue behavior and deadline behavior separately according to the declared observation policy. Do not assert identical physical schedules/latencies or universal terminal equality in noisy production runs.

**Counterexample:** the exact same correct execution finishes 1 ms before a deadline without observation and 1 ms after it with a supported bounded observer. A universal terminal-outcome equality assertion would reject correct timeout behavior or encourage weakening the deadline. The deterministic task-return regression remains a valuable rejecting case.

**Counterexample:** lost claim ACK followed by valid owner settlement observation must remain possible without launching a workload; the same observation must never start another worker. These are distinct assertions.

##### AR4 — no second runtime dispatch is narrower than exactly-once arbitrary harness tools

**Required narrow correction:** bind the guarantee to runtime-owned effects/dispatch and the selected profile's explicitly controlled effect paths. For stronger tool-effect promises, require the actual adapter's retry/idempotency/enforcement inventory and rejecting cases, including hidden SDK retries. **Counterexample:** one runtime `turn/start`; SDK tool performs a write, loses response and retries inside the same live invocation. Runtime dispatch count is one while the external write count is two. A test counting only runtime launches passes incorrectly.

**Required correction:** B/C are eligible only when the exact public mutating operation is proven repeat-safe with a durable caller identity/fingerprint, correct tenant/project binding, duplicate outcomes and a retained dedup/receipt horizon covering every supported wrapper retry/replay/restore path. The wrapper does not turn duplicate observation into dispatch ownership. If the receipt/horizon has expired or proof is unavailable, stop/quarantine the replay through the owning protocol; do not rekey or resubmit the same semantic intent. “Disable SDK retry” is useful but insufficient.

A runtime submit proof does **not** establish exactly-once execution of arbitrary model-chosen tools inside the harness. State which effect boundary is protected: runtime dispatch, provider request or downstream tool operation.

**Kill cases:** crash after external submit before wrapper journal, same key with changed fingerprint, wrong trusted scope, replay after retention expiry, restore to an older workflow snapshot, cancel followed by stale replay. Verify one protected dispatch, truthful unknown/duplicate observations and retained cleanup authority. No need to implement this before a real B/C consumer exists.

##### RF3 — P2 clarification: preserve canonical history only after its security/persistence admission

**Locations:** `modularity.md` M-H01/M-H02 and §5, synthesis table row history/reader and future redaction spike. Each passage separately is reasonable; their combined shorthand “canonical record → projection/redaction” plus “source history is immutable” can be misread as persist raw sensitive canonical data, redact only UI/telemetry later.

**Counterexample:** a registered credential appears in provider output or a diagnostic payload. The converter preserves original history in the DB to avoid mutation and masks only the reader projection. The UI test passes, while DB export/recovery/logging retains forbidden secret material. A second failure mode exempts arbitrary user-supplied IDs from redaction because they look structural.

**Evidence:** S2 lines 301–308 retain owner policy integrity and prohibit secret inventory in state/snapshots/errors; framework report F11 calls for minimization before recording. OpenHands historical fix distinguishes structural fields from sensitive content; it is not a permission to persist secrets. Mastra normalization immutability concerns already accepted source history, not bypass of security admission.

**Required correction:** say that PA/RS and the relevant owner first determine the permitted authoritative representation before persistence/export. Schema-aware sanitization/minimization must preserve structural identity/discriminants and typed reload/cursor semantics; subsequent presentation/model-input projections do not mutate that permitted source. If exact required bytes cannot be retained within security policy, emit a typed refusal/gap or an approved restricted artifact reference, rather than an invalid record or unrestricted raw copy. No new global sanitizer or universal history aggregate.

**Rejecting cases:** known secret fixture absent from every nonsecret operation/output/diagnostic persistence/export surface (PA credential custody follows its separate approved policy); controlled timestamp/enum/ID fields still decode and paginate; hostile user strings are not promoted to trusted structural identity; provider projection preserves call/result causality and leaves the permitted source unchanged.

#### Bounded clarifications; do not turn into new infrastructure

##### RF4 — Observer parity is a controlled semantic property

The off/on test should fix provider responses, IDs/clock, accepted policy and deterministic scheduling inputs with sufficient budgets. Equal semantic input gives equal canonical decision/dispatch/result. It need not produce identical wall-clock completion, telemetry schedule or terminal outcome when one run legitimately hits an elapsed deadline or an explicitly qualified resource bound. Observation remains bounded and cannot gain mutation authority; timeout/backpressure behavior needs its own tests. This independently agrees with the evidence critic's clarification.

##### RF5 — Revocation checks must match the qualified enforcement boundary

The proposed revoke-before-dispatch test is useful. For a selected remote profile, a caller-side fresh grant read does not prove that an already buffered/delayed command cannot execute after revocation. Reuse existing F12 target fencing/cutoff obligations and test the late command at the receiver where the promise requires it. Do not imply instantaneous revocation for a profile that only offers expiry/cooperative cancellation. Explicit privileged APIs must not be reachable from an untrusted agent/tool/HTTP path merely by setting a payload flag; trusted identity and allowed privileged semantics come from the accepted owner contract. This does not prohibit legitimate administrative APIs or make an untrusted-plugin requirement part of Q2-A.
